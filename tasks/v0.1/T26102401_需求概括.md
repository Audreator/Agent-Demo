## 1. 一句话目标

模型准备用“不知道 / 没有相关信息”收尾时，不让用户看到该回答，后端先强制联网检索一次；检索仍无结果或不可用，才用固定文案告知。同时在管理后台补齐首 Token 延迟 P95（总览、趋势、模型分层）。

---

## 2. 成功标准（按优先级）

1. 最终回答命中“不确定 / 拒绝”表述且本轮没有成功搜索时，用户看不到这段回答，随后出现一次真实的 `search` 工具调用。
2. 强制检索有结果时，模型基于检索结果重新作答；仍拒绝则替换为固定文案。
3. 检索为空、失败、工具离线 / 被禁用、轮次上限时，统一回复「已尝试联网检索，暂未获取到相关信息。」，不编造内容。
4. 已有成功搜索的轮次不再强制；每轮最多强制一次；`ReAct` 与 `native` 两种模式都生效。
5. 后台总览出现“首Token P95”，趋势图出现同指标曲线，模型维度按层出现“首Token P95”与样本数。
6. 旧数据无该字段时显示“—”，接口不报错、不破坏现有响应。
7. 现有 95 项测试与 ruff / mypy / pytest、npm ci / typecheck / build 全部通过，并新增覆盖本需求的用例。

## 6. 功能需求

### 6.1 不确定回答拦截与强制检索

#### 6.1.1 触发定义

同时满足以下条件才触发：

1. 模型输出被解析为最终回答（`Final Answer` 或 native 最终消息）。
2. 本轮此前没有任何一次 `search` 状态为 `ok`（不要求有结果，只要成功执行过）。
3. 最终回答命中“不确定 / 拒绝”表述，命中位置在前 200 字符内，且全文不含 `http(s)` 链接。
4. 最终回答长度不超过 800 字符（超过视为已给出实质内容，不拦）。
5. 本轮尚未强制检索过，且总开关开启。
6. 该回答不是 `wrap_up`、`parse_error`、`budget_exceeded` 或服务错误兜底。

命中示例：「我不知道」「无法确定」「没有相关信息」「未找到相关资料」「I don't know」「I'm not sure」。
否定示例：正常回答中顺带出现“不确定”但已给出完整结论与来源。

#### 6.1.2 回答缓冲与放行

- `ReAct` 模式：仅缓冲 `Final Answer:` 之后的正文，之前的思考文本继续按现有方式流式推送。
- `native` 模式：缓冲 `content`，`reasoning` 继续流式。
- 不触发：缓冲内容一次性作为单个 `message_delta` 放行，再按现有逻辑落库。
- 缓冲上限 20,000 字符；超限立即放行并跳过判定，避免内存与延迟失控。
- 模型流式中断触发重试时，缓冲内容必须清空，不得重复拼接。
- 用户可见效果：最终回答由逐字输出变为整段到达；这是本期已确认的取舍。

#### 6.1.3 强制检索执行

- 由后端直接执行 `search`，不依赖模型再次输出工具调用。
- 参数：`query` 取本轮用户输入（去首尾空白，最多 500 字符）；`max_results=5`；不传 `recency_days`、`site`。
- 复用现有工具执行器、MCP 通道、超时与重试策略；不额外增加重试次数。
- 必须完整落库 `tool_calls`（状态、耗时、摘要、引用元数据）并推送 `tool_start`、`tool_result`；`tool_result` 带 `citations`。
- 计入一次工具迭代，并受现有单轮 8 次上限约束；若本轮尚未计为任务型轮次，则计入任务型轮次。
- 写入事件 `search_forced`，payload 至少包含：触发原因、query 长度、执行状态（`ok` / `empty` / `error`）、结果条数、可访问引用数、耗时。
- 检索结果按现有规则压缩后作为 Observation 回填上下文，继续主循环让模型重新作答。
- 回填必须与当前模式协议一致：`ReAct` 追加一条 `Action: search` / `Action Input` 助手消息，再追加 `Observation` 用户消息；`native` 追加带 `tool_calls` 的助手消息与 `tool` 消息。原拒绝文本不得进入上下文。
- `search` 已在会话禁用列表、注册表缺失、MCP 离线时不得执行，直接走固定文案。

#### 6.1.4 结果处理

| 场景 | 处理 |
|---|---|
| 检索成功且有结果 | 回填 Observation，模型重答；正常放行重答内容 |
| 检索成功但结果为空 | 固定文案，不再二次强制 |
| 检索报错 / 超时 | 固定文案；事件记录 `error` 原因 |
| 工具离线、被禁用、开关关闭 | 固定文案；事件 `search_forced_skipped` 记录原因 |
| 已达 30 个任务型轮次上限 | 不检索，直接固定文案 |
| 单轮工具迭代已达 8 次 | 不检索，直接固定文案 |
| 剩余模型调用次数不足以重答 | 仍执行检索，用收束总结返回，不得展示原拒绝文本 |
| 重答后仍是拒绝表述 | 替换为固定文案，不再强制检索 |
| 检索成功但引用全部不可访问 | 视为有结果，依据内容作答，不替换 |

固定文案：「已尝试联网检索，暂未获取到相关信息。」
固定文案作为最终消息落库（`final` 或收束时为 `wrap_up`），携带 `forced_search=true` 标记，便于后台回溯。

#### 6.1.5 前端表现

- 不新增组件；强制检索会以现有工具卡片形式出现，随后出现引用列表与最终回答。
- 最终回答整段渲染，现有流式增量处理逻辑保持不变。
- 历史消息、引用、工具汇总、评价逻辑均不变。
- 断线重连按现有回放机制恢复，不新增事件类型以外的协议变化。

### 6.2 首 Token 延迟 P95

#### 6.2.1 采集

- 模型 TTFT：从向模型层发出请求到收到首个非空增量（内容、思考或工具调用）的毫秒数。
  - 每次尝试都记录到 `model_call` span payload；成功调用同时写入 `model_success` payload 的 `first_token_ms`。
  - 重试只以最终成功那次进入统计。
- 轮次首可见：从请求入口到第一个用户可见增量（`thought_delta` 或 `message_delta`）的毫秒数，写入 `turn` 事件 payload 的 `first_token_ms`。
  - 若本轮在产生可见增量前失败，则不写该字段。

#### 6.2.2 统计与展示

- 总览卡“首Token P95”：范围内轮次首可见的 P95，单位毫秒。
- 趋势图：每个时间桶的轮次首可见 P95；无样本为 `null`，前端断点显示。
- 模型维度：每层成功调用的 TTFT P95，附样本数。
- 时间范围、时区、粒度沿用现有后台规则（最大 90 天，Asia/Shanghai）。
- `null` 不计入分母；无样本返回 `null`，前端显示“—”。
- 本期不新增告警、不导出 CSV、不进入调用链明细。

| 指标 | 口径 |

## 10. 异常与边界

| 场景 | 处理 |
|---|---|
| 最终回答含“不知道”但已有成功搜索 | 不触发，正常放行 |
| 最终回答超过 800 字符或 20,000 字符缓冲上限 | 不触发，立即放行 |
| 回答中出现“不确定”但同时给出完整结论 | 由长度、位置、链接规则排除误判 |
| 强制检索超时 | 固定文案，不阻塞本轮结束 |
| MCP 整体离线 | 固定文案，不重试、不报 500 |
| `search` 连续失败被禁用 | 固定文案，记录 skipped 原因 |
| 本轮已是第 30 个任务型轮次 | 不检索，固定文案，按收束流程结束 |
| 重答仍拒绝 | 固定文案替换，不循环 |
| native 模式同时返回工具调用与正文 | 正文缓冲，工具调用正常执行 |
| 断线重连 | 按现有事件回放；最终回答为单条增量 |
| 旧数据缺 `first_token_ms` | 统计忽略，界面显示“—” |
| 后台查询范围超 90 天 | 沿用现有 400 错误 |

## 11. 风险与取舍

| 风险 | 影响 | 处置 |
|---|---|---|
| 最终回答不再逐字流式 | 所有回答的等待感增强，首 Token 指标同向变差 | 已确认选择“绝不先展示不知道”；思考仍流式；缓冲上限兜底 |
| 拒绝表述误判 | 正常回答被强制多搜一次，增加耗时 | 位置、长度、链接三重限制；事件可回收误判 |
| 真实搜索不稳定 | 强制检索放大超时与空结果 | 固定文案兜底，不抛错；内部区分 error / empty 便于统计 |
| 强制检索增加时延 | 最坏叠加一次搜索超时 | 沿用现有超时与重试；不追加二次强制 |
| 搜索与回答重复展示 | 视觉冗余 | 沿用现有工具卡片与汇总；不新增组件 |

## 12. 测试要求

- 检索为空 / 报错 / 离线 / 禁用 → 固定文案，接口 200。
- 已有成功搜索 → 不触发。
- 第 30 轮任务上限 → 不检索。
- native 模式全链路。
- `GET /api/admin/metrics` 新字段存在且数值与构造数据一致。

### 12.3 前端与回归
